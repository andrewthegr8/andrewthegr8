Work/03 — Autonomous Mobile Robot

ME 405 Mechatronics · Solo · Cal Poly

Autonomous Mobile Robot

I programmed a Pololu Romi robot that completes an obstacle course on its own using line-following, odometry, and bump sensors to hit checkpoints and dodge obstacles as fast as possible. This was a solo project and incorporates an observer-based state estimator and a custom heading-and-speed control law. I tuned it to cut course completion time from ~30 s down to ~11 s and ended up being the fastest of twelve teams.

A

The problem

The term project for the ME 405 class at Cal Poly is to program a low-cost Pololu Romi controlled by an STM32L476 Nucleo running MicroPython to autonomously complete an obstacle course. It must follow a line to a junction, then hit a sequence of checkpoints while avoiding obstacles and contacting a wall. The metric that matters most is full course completion time so the primary design question is how to know where the robot is and drive it quickly without losing control.

B

Overall approach & design decisions

Solo

State estimation

Romi's pose is estimated in real time using an observer-based state estimator. It runs by solving a state-space model (wheel velocities, heading, wheel positions, and robot X/Y position) built on a first-order motor model using RK4 integration. The model incorporates sensor feedback from the wheel encoders and IMU to return robust estimates of the robot's state. Because the model takes motor voltage as an input, I chose LiPo AA cells with built-in regulators for a stable power supply over standard alkaline batteries.

Control law

I wrote a custom heading-and-speed control law instead of using a more classic Pure Pursuit approach. Heading error is computed from the dot and cross products between the vector representing the heading of the robot and the vector from the robot to the target. This drives the rotational and linear velocities of the robot. The robot rotates so that it points at a target point and slows for large heading errors and as it approaches a waypoint, so it doesn't overshoot.

Real-time firmware & tooling

  • MicroPython is a suboptimal programming language for real time control but was a course requirement. I compensated for some of its foibles by using the @micropython.native emitter, extensively pre-allocating buffers, and manually running its garbage-collector to manage heap memory.
  • I built a full PC-side telemetry toolchain using Bluetooth to communicate with the robot. It uses custom binary packets, presents a live Tkinter dashboard, and allows for CSV export and auto-plotting of course run data.
C

Obstacles and solutions

  • Constant speed didn't work. With a fixed linear velocity, the robot would overshoot waypoints and try to backtrack, especially on tight turns. This was fixed by adding speed modulation based on heading accuracy and distance-to-target.
  • The IMU malfunctioned near the wall. Close to the metal wall the IMU's magnetometer gave nonsense headings. Since the IMU's heading is used as feedback for the observer, the estimated heading quickly degraded. To fix this, I disabled IMU feedback near the wall (computing heading from wheel velocity alone), and then re-enabled it after the BNO055's self-calibration fixed the interference issue.
  • Bluetooth corruption showed up as spikes when plotting data from the robot. Bluetooth packets would randomly be corrupted and cause very large (or small) floating point numbers which would ruin plots. This was fixed by adding a median-absolute-deviation outlier filter in the plotting engine.
  • Loop timing. Trial and error put the smallest reliable task period at 25 ms; I raised it to 30 ms for the final demo so unoptimized code wouldn't cause jitter in the control loop's timestep.
D

Results

Fastest of 12

Iterative tuning using real run data pulled course time from roughly 30 seconds to about 11 seconds — the fastest of the twelve teams. The estimator's predicted velocities and heading track the measured signals closely, which is what made driving that aggressively feasible.

E

What I'd build next

  • Do system characterization to tune the motor model. Its parameters came from theory plus basic testing. Proper motor characterization would sharpen the estimator and let me push sensor feedback gains further with less risk.
  • Simplify the control law. The final heading-speed control equation works but grew complex as I ran out of time before the demo. I'd re-derive a cleaner version now that I know which parameters are actually useful.
