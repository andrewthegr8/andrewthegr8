Work/02 — Robotic Arm

ME 507 Mechatronics · Team of 3 · Cal Poly

4.5-DOF Color-Sorting Robotic Arm

A semi-autonomous robotic arm: you use the joystick to move the end effector over a foam block, then it takes over at the press of a button. It reads the block's color and places it into the appropriate bin. It's powered by four stepper-driven joints and a servo gripper and run by a custom STM32 controller. I designed the motion subsystem and selected its electronics.

A

The problem

The ME 507 term project was to build a mechatronic device that interfaces with multiple sensors and actuators using a custom PCB. My team built a robotic arm that sorts foam blocks by color. It runs semi-autonomously; the operator levels the arm and presses the joystick to zero the joints, drives the end effector over a block using a joystick, then presses a button to hand off control to the arm. The arm reads the block's color with an end-effector sensor, closes the gripper, and moves the block to the appropriate bin for that color.

System at a glance

  • Four stepper-driven joints + a servo-actuated gripper — 4.5 DOF
  • End-effector color sensor (TCS34725) over I²C
  • Handheld joystick controller for manual positioning
  • Custom STM32H7 control PCB that drives everything
B

My role & design decisions

Motion & electronics

On the three-person team I owned the motion and actuation subsystem end to end. I selected the electronics that drive the joints and wrote the firmware that commands them. (Teammates owned the joystick/state machine and color-sensing pipelines.)

Electronics & component selection

  • Selected stepper motors based on predicted static and dynamic load torques.
  • Selected the TMC429 motion-control chips and appropriately sized stepper drivers.
  • Integrated these into our custom control PCB (designed in Fusion 360 Electronics, fabricated by JLCPCB). This board carries the STM32 microcontroller, drivers, and handles power distribution.

Motion firmware

  • Wrote a TMC429 SPI driver to facilitate the deployment of vendor provided drivers, a basic enable / safe-state control driver to interface with the stepper drivers, and a radians-to-steps command layer.
  • Built a trajectory / waypoint engine. Motions are declared as waypoint structs (per-joint targets plus gripper state), so adding a new path is a data change, not new control code.
Key decision — offload the ramping

Rather than compute full inverse kinematics on the MCU, we command position targets and let the TMC429's onboard ramp generator handle acceleration and deceleration in hardware. It cuts the real-time computational load and simplifies the code needed on the MCU while keeping the arm's motion smooth. The trade-off is coordinating joints at a waypoint level instead of a continuous Cartesian path. We also selected the STM32H7 for its double-precision FPU and higher clock speed over an STM32F4 for marginal added cost.

C

Obstacles and Solutions

  • TMC429 SPI bring-up was a nightmare. Getting the STM32 talking to the TMC429s took multiple days. Selecting the right SPI settings was complex, the clock speed for the motion controllers was initially configured incorrectly, and there was a bug in the (unofficial) vendor provided firmware. The SPI bug was found using an oscilloscope to watch the actual SPI signals.
  • After the TMC429 chips were up and running, the motors refused to move. This was traced to a bug where each motor driver's reset line was being held high (instead of low), keeping the chips in reset.
  • Six colors → four. The classifier computes hue for six colors, but in testing red, yellow, green, and blue separated most reliably. So, the final demo committed to those four rather than chase noisy edge cases.
D

Results

The arm successfully demonstrated the full loop end to end with joystick-assisted block selection, color detection, gripping, and autonomous sorting. Formal cycle-time and repeatability metrics weren't recorded, but the arm reliably and consistently sorted blocks in our demo.

E

Next Steps

  • Close the position loop. The joints run open-loop from a manual zero; adding homing switches (the PCB already has the inputs) would guarantee a repeatable origin every run.
  • Optimize place paths. Dynamically compute path to a target bin from the end effector's current position rather than returning home and using a fixed path.
  • Implement more powerful picking motions. With motor ramping offloaded, there's MCU budget to compute inverse kinematics to allow for task space control of the end effector. Ideally, the joystick would be able to command more complex motions for the arm to pick up blocks in a wider range of positions.
